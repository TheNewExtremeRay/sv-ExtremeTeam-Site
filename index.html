Fractal SafeView

“Don’t trust the file. Process it first.”

Fractal SafeView is a security-focused desktop video player that processes potentially untrusted MP4 files through full video and audio re-encoding before playback. By generating a fresh video instead of directly playing the original file, SafeView introduces an additional layer of protection between untrusted media and the playback environment.

How it works

The pipeline: decode everything, rebuild, then play

SafeView never hands the original file to the player. The media takes a full trip through FFmpeg first — and only the freshly generated output reaches the playback stage.

  1. 1

    Select an untrusted MP4

    Open a file by drag-and-drop, the file picker, Windows “Open with”, or the command line. The original is treated as untrusted input — nothing plays yet.

    input: original .mp4
  2. 2

    FFmpeg fully decodes video and audio

    FFprobe inspects the container, then FFmpeg completely decodes the original video and audio streams. The original compressed bitstream is not reused.

    stage: FFprobe → FFmpeg decode
  3. 3

    Re-encode into fresh H.264 / AAC

    The decoded frames and audio are re-encoded from scratch — H.264 video via libx264 and AAC audio — into a brand-new fragmented MP4 container.

    output: fresh H.264 + AAC · fMP4
  4. 4

    Progressive streaming over localhost

    The newly generated MP4 is streamed locally. Playback can start once roughly 1 MB of the re-encoded file is ready — you don’t wait for the full transcode.

    stage: localhost stream → MediaSource Extensions
  5. 5

    SafeView plays the processed output

    Only the freshly generated media is decoded for playback. Processing and playback are separate stages, and the original file never reaches the player.

    plays: the new file — not the original
Not SafeView

Remuxing (stream copy)

Remuxing only rewrites the container. The compressed video and audio streams inside are copied byte-for-byte:

  • Original bitstreams pass through untouched — same compressed data, new wrapper
  • Anything embedded in those streams survives the trip intact
  • The player still decodes the exact data the original file contained
  • Cheap and fast — but it changes the packaging, not the media
The SafeView approach

Full re-encoding

SafeView decodes the media all the way down and rebuilds it from the decoded frames:

  • Complete decode of original video and audio before anything is rebuilt
  • Fresh H.264 (libx264) video and AAC audio are generated from that decoded data
  • A new fragmented MP4 container is produced — the player only ever sees this output
  • The original compressed bitstream is never played

This distinction is the whole point: a remux preserves the data you don’t trust; a re-encode replaces it with newly generated media.

Features

Everything in the player

Sanitization first, but a full player underneath: SafeView is a daily-driver video player with real playback controls, not a converter with a preview window.

Sanitization & pipeline

  • Full video and audio sanitization — complete decode and re-encode before playback
  • Progressive playback — starts once roughly 1 MB of the new file is ready
  • Seeking during encoding — move around while the transcode is still running
  • H.264 and AAC output — fresh libx264 video, AAC audio, new fMP4 container

Playback controls

  • Play / pause with instant response during encoding
  • Playback speed from 0.5x to 2x, adjustable while playing
  • Volume control and mute
  • Frame stepping — move one frame at a time
  • Fullscreen and Picture-in-Picture modes
  • Screenshot capture of the current frame
  • Elapsed / remaining time display
  • Per-file playback resume — positions are remembered between sessions

Opening files

  • Drag-and-drop a video straight onto the window
  • Native file picker
  • Windows “Open with” integration
  • Command-line opening for scripted workflows
  • Keyboard shortcuts covering the whole player

Security & limitations

What sanitization is — and what it isn’t

SafeView takes an honest, engineering-first position on risk. Here is exactly what happens to your files, and where the guarantees stop.

  • Original files are not directly playedThe video you open is treated as untrusted input and is never handed to the playback stage.
  • Full decoding and re-encoding produces new mediaFFmpeg decodes the original video and audio completely, then rebuilds them as fresh H.264 and AAC streams.
  • Playback operates on the newly generated outputOnly the freshly encoded fragmented MP4 — generated locally — is ever decoded by the player.
  • Processing and playback are separate stagesThe transcode pipeline and the player are distinct: the second stage consumes only the output of the first.

“Media sanitization reduces exposure to vulnerabilities associated with directly processing untrusted media, but it cannot guarantee absolute security. FFmpeg, the operating system, Electron and other components may still contain vulnerabilities.”

SafeView security position

What SafeView does not claim

  • It does not claim to make malicious files completely risk-free.
  • It does not sandbox or isolate the playback environment.
  • It does not replace careful file handling — it is one additional layer of defense, never the only one.

Technical information

Under the hood

A desktop application built on proven, well-understood components — wired together with a strict separation between processing and playback.

Architecture
Electron desktop application with a strict main / preload / renderer process separation. Front-end built with JavaScript, HTML and CSS.
Media engine
FFmpeg and FFprobe drive the pipeline: FFprobe inspects the container, FFmpeg performs the full decode and the re-encode.
Output format
H.264 video (libx264) and AAC audio, packaged into a new fragmented MP4 container generated during processing.
Playback transport
Localhost streaming combined with MediaSource Extensions (MSE): the fresh MP4 is fed to the player progressively as it is produced.
Progressive start
Playback can begin once roughly 1 MB of the re-encoded file is ready — seeking is supported while encoding continues.
Resource safety valves
A 10-minute transcode timeout guards against oversized or pathological files, and intermediate files live in a temporary processing directory.
